# Provider expiry and cleanup review

Scope: provider-file lifetime checkpoints, cleanup scheduling, additive migration `0007`, their callers, and regression checks. Unknown legacy expiry is retained; creation time is never used to infer provider expiry. A live 80-byte synthetic Files API probe reproduced HTTP 403 after successful deletion, without model generation. [Probe evidence](validation/provider-cleanup-probe.json).

The three simplify perspectives ran in parallel, followed by all four final code-review perspectives at xhigh. All returned issues and recommendations are numbered below, including duplicates. There is no pull request and no GitHub review comment or label was posted.

1. **Fixed — Reuse review: deleted/expired files could permanently block cleanup.** [provider_files.py:16](../backend/rushes/provider_files.py#L16) accepts authoritative elapsed expiry as sufficient to stop deletion attempts. HTTP 403 alone remains insufficient. Pending work still requires successful cleanup or known expiry before another upload.
2. **Fixed — Reuse review: upload lifetime was discarded.** [inference.py:192](../backend/rushes/inference.py#L192) captures the provider's actual expiration timestamp immediately after upload, before the checkpoint callback or generation.
3. **Addressed conservatively — Reuse review: planning age does not prove expiry.** [maintenance.py:66](../backend/rushes/maintenance.py#L66) uses the stored provider expiry. Migration `0007` adds nullable columns without guessing from window creation time.
4. **Alternative declined — Reuse review: inventory reconciliation would need credential provenance.** [provider_files.py:16](../backend/rushes/provider_files.py#L16) does not reconcile HTTP 403 against inventory listings. A fingerprint of unchanged credentials cannot prove unchanged permissions; the smaller authoritative-expiry approach avoids this inference and extra inventory calls.
5. **Fixed — Quality review, duplicate: a repeated delete returning 403 could prevent resumption indefinitely.** [activities.py:410](../backend/rushes/activities.py#L410) passes the recorded expiry into cleanup; unknown/future expiry remains conservative.
6. **Fixed — Quality review, duplicate: authoritative expiry was lost.** [activities.py:457](../backend/rushes/activities.py#L457) persists the name and expiry together before the analyzer continues. Result persistence also retains expiry when the checkpoint itself fails.
7. **Fixed — Quality review: twenty old cleanup failures could starve newer files.** [maintenance.py:70](../backend/rushes/maintenance.py#L70) excludes unresolved attempts until their one-hour retry time; known expired files remain eligible. The batch stays bounded at twenty.
8. **Retained — Quality review: unknown/future 403 must fail closed.** [provider_files.py:16](../backend/rushes/provider_files.py#L16) continues raising these errors. Naive timestamps are also treated as unknown, and a listing or credential fingerprint is not treated as deletion proof.
9. **Implemented — Quality review: exercise expiry, 403 retention, resume, and stored-response preservation.** [test_provider_files.py:1](../tests/test_provider_files.py#L1), [test_provider_budget.py:121](../tests/test_provider_budget.py#L121), and [test_production_regressions.py:194](../tests/test_production_regressions.py#L194) cover these boundaries without paid generation.
10. **Fixed — Efficiency review, duplicate: deleted-file 403 caused repeated work.** [provider_files.py:4](../backend/rushes/provider_files.py#L4) recognizes only known elapsed expiry and avoids constructing a provider client for that case.
11. **Fixed — Efficiency review, duplicate: oldest-first failures starved cleanup.** [maintenance.py:90](../backend/rushes/maintenance.py#L90) orders eligible attempts and records a retry delay after failure. Both success and failure writes check that the file name and expiry still match their snapshot.
12. **Fixed — Efficiency review, duplicate: discarded expiry caused unnecessary remote work.** [inference.py:192](../backend/rushes/inference.py#L192) retains the initial upload's expiry even if later polling replaces the SDK file object.
13. **Fixed — Final reuse pass: removing the key disabled expiry-only maintenance.** [maintenance.py:117](../backend/rushes/maintenance.py#L117) always sweeps workspaces; without credentials, the query selects only files whose authoritative expiry has passed.
14. **Fixed — Final efficiency pass, duplicate: expired files remained stuck without credentials.** [test_production_regressions.py:249](../tests/test_production_regressions.py#L249) exercises the real maintenance loop without a key and verifies no provider client is needed.
15. **Fixed — Final quality pass: the live verifier used the old callback arity.** [verify_gemini.py:49](../scripts/verify_gemini.py#L49) accepts both checkpoint arguments. An offline verifier test invokes the updated callback and checks its report, without calling a live provider.
16. **Fixed — Final quality pass: a fake upload object omitted the SDK expiry field.** [test_review_regressions.py:496](../tests/test_review_regressions.py#L496) includes the nullable field so the test reaches its intended model-budget validation.
17. **Fixed — Final testing review: the fairness test removed the key, independently excluding the twenty failures.** [test_production_regressions.py:194](../tests/test_production_regressions.py#L194) now runs both keyed and offline variants. The keyed second pass reaches the later file without retrying the twenty delayed failures; the offline variant separately tests the maintenance loop.
18. **Fixed — Final testing review: the actual database upload checkpoint lacked interruption coverage.** [test_provider_budget.py:240](../tests/test_provider_budget.py#L240) calls the activity's real upload callback from a fake analyzer and then raises.
